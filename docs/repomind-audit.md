# RepoMind Audit

## 1. Current Architecture

The Python implementation matching this historical audit was an external RepoMind checkout inspected read-only. A separate frontend checkout was also inspected and did not contain the Python ingestion/retrieval pipeline audited here. Local checkout paths are intentionally omitted from this release copy. The Python project's `README.md` describes Postgres/pgvector, ingestion, retrieval, and evaluation; the implementation is in `src/repomind/` (`cli.py`, `ingest.py`, `chunking.py`, `embedding.py`, `retrieval.py`, `models.py`, `db.py`, `api.py`, and `evaluation.py`).

The CLI (`repomind.cli`) initializes the database and ingests a repository. The FastAPI app in `src/repomind/api.py` exposes `POST /query`; it calls `retrieval.vector_search` and returns retrieved evidence and a heuristic confidence summary. This is a retrieval service, not an autonomous answer-generation system. `pyproject.toml` declares FastAPI, Uvicorn, Pydantic Settings, SQLAlchemy, psycopg, pgvector, Sentence Transformers, rank-bm25, GitPython, tree-sitter, and httpx; the `dev` extra declares pytest and Ruff. `rank-bm25` is declared but not used by the current retrieval code. `docker-compose.yml` defines a PostgreSQL 17/pgvector service and a persistent named volume.

## 2. Retrieval Capability

`src/repomind/api.py::query` accepts a query and `top_k` from 1 to 50. It calls `src/repomind/retrieval.py::vector_search(session, query, k)`, which embeds the query with `src/repomind/embedding.py::embed` using the configured Sentence Transformers model (default `sentence-transformers/all-MiniLM-L6-v2`), then orders chunks by pgvector cosine distance and limits the result count to `k`. Embeddings are normalized; `vector_search` returns `1 - cosine_distance` as the rounded similarity score.

`Retrieved` contains `chunk_id`, `content`, `source_type`, `metadata`, and `score`; the API also returns the query and retrieval latency. Metadata currently carries `path`, `occurred_at`, `source_id`, and chunking metadata. `src/repomind/ingest.py::_stable_chunk_id` makes chunk IDs deterministic from source key, ordinal, and content. File `source_id`s are repository-relative paths; commit source IDs are commit SHAs. There are no line or byte ranges and no explicit retrieval-method field, though the current method is vector search. A future ToolProvider wrapper is feasible around `vector_search`, with repository selection and a stable serialized result contract added at that boundary; it is not present now.

## 3. Ingestion Pipeline

`src/repomind/ingest.py::ingest_repo` resolves the repository path, walks supported text files, sorts them, reads text, classifies it as code/doc/ADR, selects fixed or Python tree-sitter AST chunking, prepares/upserts the document, embeds changed chunks, and commits. It optionally ingests Git commits as separate documents. `src/repomind/chunking.py::fixed_chunks` and `ast_python_chunks` assign zero-based, increasing ordinals per document; the AST path records symbol and node type but not source ranges.

`SourceDocument.id` in `src/repomind/models.py` is a random UUID on creation. Reingestion finds the existing document by `(source_type, source_id)`, protected by `uq_source_document_type_id`, and reuses its UUID. Chunk IDs are deterministic UUIDv5 values; `uq_chunk_doc_ordinal` enforces one chunk per document ordinal. The schema has no declared foreign key or ORM relationship from chunks to documents; deletion is handled explicitly by `_prune_deleted_file_sources`.

Unchanged content and chunking mode take a hash/ordinal fast path in `_prepare_source`, so sequential repeated ingestion reuses existing chunks. Changed chunks are replaced, and a complete (unbounded) scan prunes removed file sources. `max_files` disables pruning because that scan is partial. This is sequentially idempotent for unchanged input, but concurrent ingests are not serialized, failed files are skipped, and source uniqueness omits a repository identifier: indexing multiple repositories in one database can collide on identical relative file paths or merge their identity. File traversal also follows file symlinks via `Path.is_file()`/`read_text()` without verifying the resolved target remains inside the repository.

## 4. Duplicate Chunk Failure

The current-code cause is replacement ordering, not random document IDs, ordinal generation, or stale rows. For a changed chunk at an existing ordinal, `src/repomind/ingest.py::_prepare_source` schedules `session.delete(current)` (around lines 182–192), then `_persist_source_chunks` adds a replacement with the same `document_id` and `ordinal` (around lines 201–218), and `ingest_repo` commits both together (around lines 303–306). SQLAlchemy's flush can issue the INSERT before the DELETE, violating `uq_chunk_doc_ordinal` in `src/repomind/models.py`.

I reproduced that unit-of-work ordering with an isolated in-memory SQLAlchemy table using the same `(document_id, ordinal)` unique constraint: delete-old/add-new in one commit raised `IntegrityError: UNIQUE constraint failed: chunks.document_id, chunks.ordinal`. This confirms the mechanism without touching the external RepoMind database. Docker Desktop's daemon was unavailable, so a PostgreSQL reproduction was not possible in this audit. The existing per-file exception handler rolls back and counts/logs the failure; it does not repair the conflicting flush order. Stable source keys and sequential upserts keep document IDs stable after first creation; chunk ordinals are generated sequentially. A database unique constraint is appropriate, but the delete/insert ordering is the failing path. A concurrent ingestion race is a separate unguarded risk, not needed to explain this observed error.

## 5. Database and Vector Retrieval

`src/repomind/models.py` stores 384-dimensional `Vector` embeddings and the two uniqueness constraints described above. `src/repomind/db.py::init_db` enables the pgvector extension and creates tables. `_ensure_vector_index` creates an IVFFlat cosine index only when chunks already exist; `init_db` calls it before a first ingestion, while `ingest_repo` does not call it after ingestion. Therefore a fresh database normally uses exact sequential vector scans until the documented manual index call is made. This remains functionally usable for small corpora, but is not an operationally ready large-repository retrieval service.

`retrieval.vector_search` performs real top-k cosine ranking and returns a score, but it has no repository filter and no BM25 fusion or reranker. The 384-dimensional model/database contract must remain aligned. The API and query code were inspected, but no live vector query was run because the Docker daemon and PostgreSQL service were unavailable. Vector retrieval is technically implemented; its live database behavior and scale are unverified here.

## 6. Evaluation Harness

`scripts/evaluate_recall.py::evaluate` expects JSONL rows with a `query` and `relevant_source_ids` and/or `relevant_chunk_ids`. It runs `vector_search` for each row and computes Recall@K, Precision@K, reciprocal rank/MRR, binary nDCG@K, average retrieval latency, p95 latency, and average top-1 score using `src/repomind/evaluation.py`.

The current `eval/eval_set.jsonl` has 50 unique queries and source labels on all rows, no chunk labels. That size is within `eval/README.md`'s suggested range. Its trustworthiness is not established: `docs/target_repo_verification.md` says the target FastAPI corpus was not locally ingested and labels/results were deliberately not generated, while `README.md` says the baseline is blocked until the eval set exists; nevertheless the checkout contains a populated eval set plus `results/vector-baseline.json`, `results/vector-baseline-frozen.json`, and `results/ast-vector.json`, each claiming 50 queries. This checkout has no `.git` metadata, so label/result provenance or a frozen commit cannot be checked. No metrics were regenerated for this audit, and the existing results should not be treated as verified benchmark evidence.

For the present source-only labels, the metric implementations are broadly recognizable, but mixed chunk+source labels are counted additively in Recall/nDCG while Precision treats a result position as one binary hit; a result matching both label types can therefore have inconsistent metric semantics. `evaluate` times each `vector_search` call, including query embedding; there is no explicit warm-up or repeated-run protocol, so the first model load can skew latency and database/cache conditions are uncontrolled. The dataset's semantic correctness, label independence, and relationship to an ingested corpus cannot be confirmed from this checkout. The harness is useful scaffolding, but the current evaluation set and existing result files are not trustworthy enough for a benchmark claim.

## 7. Integration Boundary

Do not expose SQLAlchemy sessions, model objects, or the database directly to flagship agents. The smallest future boundary is a retrieval provider method such as `search(query, repository_id, top_k) -> RetrievalResult`, where each evidence item serializes `chunk_id`, stable `source_id`, repository-relative `path`, optional source range, `source_type`, `text`, `score`, and `retrieval_method`; the result should also preserve the query and timing. This maps cleanly to `Retrieved` while leaving the backend replaceable. Add the repository filter and stable source/range metadata before exposing it. No ToolProvider or flagship code was added during this audit.

## 8. Required Fixes Before Integration

At the time of the initial audit, the changed-chunk flush-order bug and two test failures were open. The stabilization work and their resolutions are recorded in section 10. Remaining integration blockers are repository-scoped document identity and retrieval, source/document/range metadata, automatic post-ingest vector-index setup, live PostgreSQL/pgvector validation, reproducible model/runtime validation, and evaluation-artifact provenance. Symlink containment and the schema's missing document/chunk foreign key should also be addressed before indexing untrusted repositories.

## 9. Recommended Next Step

Treat this implementation as a promising vector-retrieval prototype, not as an integration-ready retrieval dependency. Next establish an isolated reproducible PostgreSQL/pgvector environment, validate a pinned corpus and retrieval results, and resolve repository isolation and evidence metadata before designing an adapter. Do not integrate RepoMind yet.

## 10. Stabilization Results

- **Ingestion fix:** `src/repomind/ingest.py::_prepare_source` now calls `session.flush()` after scheduling stale/replaced chunk deletions and before returning pending replacements. The deletes execute before `_persist_source_chunks` adds rows at the same `(document_id, ordinal)`. The flush remains inside the same transaction, so subsequent embedding/insert failures can still roll back the whole file update.
- **Regression and idempotence:** `tests/test_ingest_classification.py::test_changed_content_same_ordinal_is_replaced_and_reingest_is_idempotent` uses the production SQLAlchemy models and an isolated in-memory SQLite database. It ingests a file, reingests it unchanged (same chunk ID reused), changes its content without changing path/ordinal (replacement succeeds, one row remains, document ID is retained), and ingests unchanged content again (replacement chunk is reused). This verifies the ordering fix against the same SQLAlchemy uniqueness constraint, but is not a PostgreSQL test.
- **Prior test failures:** `test_ingest_rolls_back_failed_file_and_continues` had an incorrect commit count: successful-file persistence and the full-scan pruning phase each commit, so the expectation now reflects both. `test_ingest_prunes_deleted_file_sources` used a string-returning `select` mock incompatible with production's SQLAlchemy `.where()` call; its fake session now inspects the real Select and applies its document filter. Assertions remain meaningful.
- **Test result:** 31 passed. Tests ran on Python 3.12.4 with pytest 7.4.4, using runtime packages from the checkout's `.venv`; `pyproject.toml` declares pytest `>=8,<9`, while that checkout venv does not include pytest. `tests/conftest.py` now supplies deterministic Torch/SentenceTransformer stubs because model loading is not under test. The actual Windows Torch `WinError 1114` remains an environment/runtime issue and model inference was not validated.
- **PostgreSQL validation:** Not run. Docker CLI exists, but Docker Desktop's daemon pipe is unavailable and localhost port 5432 is unreachable. No container, database, or migration was created; no live ingestion or pgvector query is claimed.
- **Vector retrieval:** `tests/test_retrieval.py` verifies query embedding input, ascending pgvector cosine-distance ordering in the generated statement, top-k limit, similarity conversion, chunk identity, file path metadata, and API serialization/top-k forwarding. Code inspection and these mock/session tests support logical correctness. The actual Postgres/pgvector execution path remains unverified.
- **Evidence metadata:** Current results include chunk ID, file path, source ID, retrieved text, and score. They do not expose repository identity, document ID, or line/source ranges. Those fields remain future schema/API work; no integration schema change was made here.
- **Repository isolation:** Not safe for multiple repositories in one database. `SourceDocument` uniqueness is only `(source_type, source_id)`, file source IDs are relative paths, stable chunk IDs use that path, and `vector_search` has no repository filter. Identical paths/content across repositories can collide or be conflated. This was documented, not redesigned.
- **Evaluation artifacts:** `eval/eval_set.jsonl` is syntactically valid: 50 unique non-empty queries, each with non-empty string source labels. The backup is byte-identical. Existing result JSON files parse and report 50 queries at k=5, but contain no dataset digest, target commit, or generation timestamp. The checkout has no Git metadata; its README/verification doc also conflicts with the presence of the labeled set and result files. Thus correspondence, independence, and provenance cannot be established: mark the eval set and all existing results **UNTRUSTED**. No evaluation was run, and no evaluation artifact was modified.
- **Remaining blockers:** Live PostgreSQL/pgvector validation; repository-level identity/filtering; document ID and source-range metadata; index creation/tuning after ingestion; actual embedding-model operation in a supported environment; and auditable evaluation provenance/metric protocol. No flagship integration, ToolProvider, orchestration, MCP, or CodeAgent-MCP change was made.
